## 3. Improvements to reduce diff and improve readability/stability

### 3a. Duplicate `is_external_signer_mode_configured` helper

The function:
```rust
fn is_external_signer_mode_configured(state: &Arc<AppState>) -> Result<bool, APIError> { … }
```
is copy-pasted identically in both `src/routes.rs` and `src/sdk/mod.rs`.

**Fix:** Move it to `src/utils.rs` or `src/sdk/mod.rs` (shared location accessible to both) and
call through from `routes.rs`. Two lines of change.

---

### 3b. `rgb_signer_descriptors_for_psbt` — key-scanning loop up to 10,000 is brittle

In `src/rgb.rs`:
```rust
for idx in 0u32..10_000 {
```
This brute-force scans 10k indices × 2 xpubs × 4 derivation patterns = up to 80k point
derivations per PSBT input in internal mode. It runs synchronously on a wallet-lock-held path.

**Fix:** In internal mode (where `external_signer` is `None`), skip the descriptor inference
entirely; the BDK wallet's own `sign_psbt` does not need these descriptors. Only compute
descriptors when `external_signer_mode == true`, and use the `signer_meta` path exclusively then
(which doesn't brute-force). The fallback `infer_keyindex_from_script` should only run when the
external signer itself returns `None` metadata (i.e. as a graceful degradation).

---

### 3c. `RgbLibWallet` mutex poison recovery in `get_rgb_wallet` adds a silent state corruption path

```rust
Err(poisoned) => {
    tracing::error!("RgbLibWallet mutex was poisoned …");
    poisoned.into_inner()   // recovers poisoned guard
}
```
Recovering from mutex poisoning means continuing with potentially inconsistent wallet state.
This was added as a "don't abort on panic" heuristic for C FFI — correct for the C boundary,
but dangerous if exposed to the wider Rust call-sites which may proceed and persist corrupt state.

**Fix:** Gate the poison recovery behind `#[cfg(feature = "uniffi")]` or `#[cfg(any(feature = "uniffi", feature = "c-ffi"))]`. In non-FFI builds, keep the `unwrap()` so panics propagate normally
and bugs surface quickly.

---

### 3d. `ChangingStateGuard` RAII struct is useful but could be a shared utility

`unlock_with_attached_external_signer` in `src/sdk/mod.rs` defines a local RAII guard:
```rust
struct ChangingStateGuard { … }
```
The existing `unlock` function does the same thing manually. Extracting this guard to a shared
location (e.g. `utils.rs`) would DRY up both unlock paths and make it harder to introduce a bug
where state is not reset on error.

---

### 3e. `external_node_id: Option<String>` — use `PublicKey` directly

`UnlockedAppState.external_node_id` stores a hex string and re-parses it in `runtime_node_id()`:
```rust
if let Ok(pubkey) = PublicKey::from_str(node_id) { return pubkey; }
```
Store `Option<PublicKey>` instead. The parsing happens once at unlock time and the `String` form
can be printed on demand. Avoids a silent failure path (if the stored string is ever malformed,
`runtime_node_id()` silently falls back to the internal key).

---

### 3f. `#[allow(dead_code)]` on `ExternalSignerUnavailable` and `get_attached_external_signer` / `set_attached_external_signer`

Three items are marked `#[allow(dead_code)]` in production code:
- `APIError::ExternalSignerUnavailable` in `src/error.rs`
- `AppState::get_attached_external_signer` and `set_attached_external_signer` in `src/utils.rs`
- `NodeKeySource::External` in `src/core_types.rs`

These exist because the attach path goes through UniFFI/C FFI but the REST route handler doesn't
use it. Either:
- Remove the `#[allow]` and let the compiler tell you which callers are missing (then add them), or
- If these are intentionally future-facing, leave a `// used by UniFFI path` comment and remove
  the `#[allow]` so future dead-code regressions are caught.
