RGB library migration scope
===========================

This change starts from RLN ecc69f20308231400561f6f060fea88acfa40cc4 and
migrates the wallet graph to UTEXO-Protocol/rgb-lib-bfa. Cargo.lock and the
rust-lightning submodule record the exact candidate revisions. It does not
adopt draft RLN #211's global on-chain-only build, VSS removal, or vendored
reqwest/native-tls workarounds.

Protocol-1.0 transfers
---------------------
Use sendrgbinvoice (SDK/UniFFI) or POST /sendrgbinvoice for a fungible invoice.
The request contains the complete invoice, asset_id, integer amount,
optional witness_data, donation, fee_rate and min_confirmations. Native
code checks network, asset, invoice amount and receive mode, then retains
the recipient's public key, encryption preference and invoice expiration.
It supplies the configured sender proxy and bounds the operation deadline
to leave the protocol's ACK/release interval before invoice expiration.
Proxy witness blinding is derived by the library; caller-specified blinding
is rejected. The library performs recipient-key, proxy and transaction
validation before signing. Existing legacy recipient-group requests do not
contain the necessary authentication data and explicitly direct proxy
callers to the complete-invoice method. Out-of-band requests remain distinct.

decode_rgb_invoice returns the additive public_key and encryption fields.
The deprecated proxy_recipient_id is absent in protocol 1.0 and is nullable.
The encryption values are Required, Optional and Unsupported. A sender must
honor the invoice preference, rather than downgrade it to fit an old DTO.

Public contract import uses rgb-lib-bfa's validated standalone registration
API with the expected asset ID supplied before mutation. It imports actual
metadata/stock and no allocations. Inspection alone is not asset admission.

Burn requests retain a generic 32-byte commitment boundary. New RGB burn_reason
is the hex encoding of these exact bytes; RLN does not interpret them as an
EVM address or claim they satisfy a bridge's destination-preimage protocol.
Bridge V1 destination validation/commitment construction belongs above this
boundary and must be independently tested.

VSS
---
The transport/crypto implementation in src/rgb_vss.rs retains the encrypted
stream version from UTEXO-Protocol/rgb-lib commit
1b951af0c8233308c919975552487be19ad2a930 (MIT). Snapshot preparation and
conditional acknowledgement use the new library's public primitives.
Manifest version 2 uses generation-specific immutable chunk keys, embedded
encryption metadata/fingerprint and a ciphertext SHA-256. Chunks are written
first without overwriting the previous generation; manifest CAS and canonical
readback happen before local acknowledgement. Interrupted or uncertain uploads
retain their orphan generation keys for diagnosis. Legacy manifest format 1
requires a separate fresh migration test store and is explicitly rejected;
this change does not claim old-format backup migration.
Creating an archive does not clear backup dirtiness. The exact content token
is acknowledged only after the remote upload succeeds; a changed token
returns an error and leaves the current state pending.

RgbLibWalletWrapper owns the one VSS client. Its wallet guard checkpoints
dirty state on release when the client's automatic policy is enabled.
Manual backup is available with automatic backup disabled. Maintained
binding policy may persist a separate default-on preference, disable this
automatic hook, and call rgb_vss::backup_wallet while holding its own single
wallet admission mutex. That helper never acquires the wrapper mutex again.
Policy callers must persist their intent and complete catch-up before
enabling automatic backup; changing the in-memory flag alone is not durable
policy or proof of a completed backup.

Only encrypted snapshots are supported: the new database contains proxy
operation keys, so the old plaintext BDK-file redaction is insufficient.
Restore authenticates/decrypts before bounded admission. Limits match the
maintained binding: 128 MiB raw archive, stream-tag-adjusted ciphertext,
512 MiB expanded, 25,000 entries and an expansion ratio of 2000 per entry.
Manifest data is bounded to 64 KiB and encryption metadata to 4 KiB.
Archive paths, entry types, duplicate names and fingerprint are checked in
an isolated staging directory before rename. Existing wallets are not
overwritten; normal online consistency and wallet-setting checks still run.

Channel funding and durable sweeps
-----------------------------------
The candidate RGB prerequisite now supplies dedicated fixed-zero-locktime
send_channel_funding_begin and send_btc_channel_funding_begin APIs. RLN routes
its explicit Some(0) channel construction into these builders; nonzero overrides
remain rejected. The library chooses final locktime before PSBT completion and
before txid-bound reservation/consignment persistence. Ordinary on-chain send
builders remain unchanged. A post-persistence PSBT rewrite is not a substitute.

Prepared channel sweeps use color_psbt_and_prepare_consume with at least one
confirmation and no expiration. The library durably records the exact unsigned
PSBT, fascia, complete consignments and protected batch without consuming RGB
state. RLN writes its KV receipt, verifies it against the canonical native
record, then marks handoff before any external signing. PSBT metadata and proof
bytes must match, even if an altered receipt has the same transaction ID.
Duplicate proof assets fail closed. KV bytes and fixed-width bincode decoding
are bounded to 32 MiB, with checked component/count admission before allocation.

A caller stopped before its first KV write recovers the library-owned operation
by exact input set, preserving its original PSBT/proofs/fee. Partial overlap and
unreadable/colliding preparations reject a new sweep. KV-write failure cancels
only the dedicated never-handed-off preparation; generic transfer failure cannot
release protected inputs. consume_transfer_fascia independently resolves the
exact confirmed native witness and commits RGB stock, spent inputs, reservations
and phase atomically. It is idempotent after consumption. RLN removes its receipt
only after successful native consumption; failed reconciliation retains it.
These source integrations require the new graph's funded regression results;
the presence of the APIs alone is not generic Lightning qualification.

Explicit compatibility limits
------------------------------
Iris's maintained on-chain profile is selected by its caller. This change does
not globally disable Lightning. IFA link rights/link operations and linked-contract
metadata remain unavailable in rgb-lib-bfa. Requests fail explicitly before signing
or RGB mutation; optional legacy link metadata stays unavailable. Negative IFA
acceptance is not a claim of linked-contract or linked-Lightning feature parity.

Address generation is fresh-only. Both address and rotateaddress reveal fresh
native addresses. reuse_addresses=true is rejected by direct SDK creation and
standalone daemon startup before wallet files are created, preserving existing
wallet data. Tests cover default/false configuration, funded rotation, restart,
same-seed recovery and funded VSS restore under this supported fresh-only policy.
Pinned-address behavior is not recreated or silently enabled.

LDK creates temporary wallet handles outside the maintained on-chain wrapper.
General Lightning + VSS cross-handle snapshot serialization and full channel
lifecycle acceptance remain separately evidenced. No legacy production-wallet
migration or hosted bridge operation is established by these changes.

External-signer VSS credential limitation
-----------------------------------------
External-signer mode still deterministically derives VSS signing/encryption
credentials from public bootstrap material (node ID, account xpubs, fingerprint
and protocol version). Those inputs are not a signer-held secret. Anyone knowing
the complete bootstrap can reconstruct the same VSS credentials; encrypted cloud
payloads do not establish confidentiality or exclusive cloud authorization against
that observer. Secret-backed derivation requires an external-signer API change.
This integration preserves existing behavior and does not claim to fix that limit.
The internal-mnemonic derivation is a different identity and is not substituted
for external signing. Proxy operation keys remain sensitive backup content.

CI integration contract
-----------------------
The standalone REST binary and the native library share complete-invoice send
execution. REST does not reference the library-only SDK module. Both callers
retain their unlocked-session guard through external signing and send completion;
invoice recipient keys, encryption and expiry admission remain mandatory.
UniFFI error-mapping tests live with the UniFFI module rather than a shared module
that is also compiled into the standalone daemon.

The local regtest fixture pins RGB Tools proxy 0.4.0 by immutable image digest and
requires server.info protocol_version 1.0 before wallet tests. Fixture PoW remains
on with maximum difficulty 4; production proxy policy is not changed. The older
0.3.0 image speaks protocol 0.2 and is not compatible with these native sources.

Legacy IFA-link success tests cannot establish parity against a library without
link rights. Explicit funded rejection tests instead require HTTP 400 and verify
unchanged assets, outputs and transaction history. Ordinary IFA issuance remains
supported. This negative acceptance is a documented missing feature, not a claim
that linked-contract or linked-Lightning payments work. Generic channel-funding
and sweep regression gates remain required; their tests are not waived.

Authenticated batch sends
-------------------------
REST /sendrgbinvoices and SDK sendrgbinvoices accept complete invoices for a
single native batch. Each group names one asset; each recipient carries its
original invoice, concrete assignment and optional witness data. The SDK uses
InvoiceAssetRecipients/RgbInvoiceRecipient/SendRgbInvoicesRequest and the existing
AssignmentKind vocabulary. REST uses recipient_groups with asset_id and recipients
containing invoice, assignment (the existing tagged Assignment) and witness_data.
The existing single fungible sendrgbinvoice API and legacy constructors are kept.
Legacy keyless proxy requests remain rejected; out-of-band legacy sends remain
supported. A batch is never emulated by multiple independent sends.

Every invoice is checked against the selected network, asset and assignment,
including Any versus a zero fungible placeholder. Witness requirements, proxy
recipient keys, encryption and expiration are preserved from the original invoice.
Admission rejects duplicate canonical asset groups and duplicate recipient aliases
within an asset. Both transports enforce at most 64 asset groups, 256 recipients,
16 KiB per invoice and 1 MiB total invoice bytes before conversion/dispatch. All
invoices must pass before unlocking/signing/mutating; one shared operation deadline
then leaves the normal ACK/broadcast margin. The old SDK/REST funding fixtures now
retain the receiver-issued complete invoice instead of reconstructing credentials
from a recipient ID. A dedicated funded mixed NIA witness/NFT test requires a
single transaction, a single positive fee and settled balances for both assets.

Candidate source and qualification
----------------------------------
Cargo.toml, Cargo.lock and the rust-lightning gitlink are the exact source graph
for this candidate. Dependency merges and new funding/sweep primitives invalidate
any assumption that earlier native binaries or published beta.5 qualify it.
Earlier host, emulator and platform evidence belongs to its recorded source;
it is not carried forward as acceptance of the graph in this PR.

Source formatting, shell syntax, Python fixture syntax and a disposable public
proxy 0.4.0 server.info probe are recorded for these repairs. Rust type checking,
focused admission/phase tests, genuine funded mixed batch and generated SDK flows,
VSS restore, ordinary/channel funding and prepared sweep lifecycle require the
final source graph and passing CI/local qualification before merge-readiness.
The merge-order ancestry gate remains unchanged: the pinned LDK revision must be
reachable from rust-lightning dev after its prerequisite PR is merged.

No hosted bridge has been operated. No merge, package publication or all-platform
native artifact qualification is established by this unpublished source work.
